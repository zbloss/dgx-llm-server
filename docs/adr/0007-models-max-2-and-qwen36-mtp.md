# ADR 0007: `--models-max 2` and MTP for qwen3.6-35b-a3b

**Status:** Accepted
**Date:** 2026-08-15
**Amends:** ADR 0005 (revisits the `--models-max 2` alternative it explicitly deferred)

## Context

ADR 0005 kept `--models-max 1` and flagged `--models-max 2` as worth revisiting "once VRAM headroom is measured in practice." That measurement happened by accident: a `docker compose logs` capture showed the coding session (`qwen3.8-27b`) and `repowise`'s post-commit background job (`qwen3.6-35b-a3b`, real LLM calls for doc/decision generation, confirmed 1-10 minutes per run) fighting over the single resident-model slot. Across the captured log: **53 `unload_lru` events, 46 force-kills, 33 of which killed a model mid-load, and 38 hard `500 failed to load` responses** — for both profiles, not just one. Zero of the 38 failures were an actual CUDA/OOM error; every one was the router evicting a model that was still in the middle of loading because a request for the *other* profile arrived first. This is what "extremely slow" coding-session responses turned out to be: not slow inference, but repeated full reloads (and outright request failures) from a structural single-slot bottleneck.

Separately, the same session that surfaced this ran 4 concurrent issue-implementation subagents against `qwen3.8-27b`. With `parallel = 2`, only 2 of those 4 requests could be served at once; the rest queued behind a busy slot. The first draft of this ADR raised `parallel` to 4 (131072 tokens/slot instead of 262144) to fix that — reverted before deploy once the same `logs.txt` was checked for actual per-request context sizes: of 344 completed requests, **48.5% (167) already exceeded 131072 tokens**, with a max of 191788. Zero ever exceeded 262144. `parallel = 4` would have silently truncated something close to half of all real turns to solve a problem (`--models-max 1`'s cross-model contention) that had nothing to do with `parallel` in the first place.

## Decision

- **`--models-max 1` → `2`.** Both current profiles (`qwen3.6-35b-a3b`, `qwen3.8-27b`) now stay resident simultaneously — no eviction between them at all, since there are only 2 profiles. Eviction only fires again if a 3rd profile is ever added. No genuine OOM was observed anywhere in the captured log at the current memory footprint, and `--models-max` only changes *how many* models' weights + KV caches are resident, not the size of any one — so this is a bet that DGX Spark's 128GB unified memory holds both (~22GB + ~18GB weights, plus the KV cache budgets below), not a re-tuning of either model's footprint. Watch `nvidia-smi`/`docker compose logs` after deploy for a genuine OOM this time; if one shows up, the fallback is reverting this one line.
- **`parallel` stays at 2** (262144 tokens/slot) on both profiles — see Alternatives for why raising it was tried and reverted. `--models-max 2` alone already fixes the contention that prompted the `parallel=4` experiment: concurrent requests within one model now queue for a free slot instead of the whole router evicting a different model, which is a much smaller cost than truncating real context.
- **`qwen3.6-35b-a3b`'s GGUF source: `unsloth/Qwen3.6-35B-A3B-GGUF` → `unsloth/Qwen3.6-35B-A3B-MTP-GGUF`.** ADR 0005's config never set `spec-type = draft-mtp` for this profile because the plain GGUF's target file doesn't contain MTP tensors (confirmed again here: `hf_fs ls` on the old repo has no separate MTP file, and the comment in the pre-existing `config.ini` already documented the load failure this causes). The `-MTP-GGUF` repo ships a `Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf` ~500MB larger than the plain one — consistent with bundled MTP tensors — plus the same `mmproj-BF16.gguf`. `spec-type = draft-mtp` / `spec-draft-n-max = 2` added to match `qwen3.8-27b`'s existing config. **Unverified pending deploy** — watch `docker compose logs` for the same "context type MTP requested but model doesn't contain MTP layers" error on first load; if it recurs, revert to the plain GGUF and drop `spec-type` for this profile.
- **`load-on-startup` swapped**: `qwen3.6-35b-a3b` → `false`, `qwen3.8-27b` → `true`. `qwen3.8-27b` is the interactive coding session's model; it should be the one warm immediately after a restart. `qwen3.6-35b-a3b` (repowise's model, called only from a background post-commit hook) can cold-load lazily. With `--models-max 2` this only affects which one is ready at boot, not which one stays resident afterward — both do, permanently, until a 3rd profile is added.

## Alternatives considered

**Leave `--models-max 1`, just fix repowise's model choice or scheduling instead.** Would reduce collision frequency but not eliminate it, and doesn't address that the failure mode isn't "a bit slower" but outright request failures (mid-load kills). Rejected — `--models-max 2` removes the entire class of failure for the two profiles that actually exist today, for a memory cost that's a known, bounded quantity (both models' weights + KV budgets), not an open-ended one.

**`parallel = 4` (131072 tokens/slot) for more subagent concurrency.** Tried first, reverted: checked against the same `logs.txt`, 48.5% of 344 real completed requests already exceed 131072 tokens (max 191788), so this would have started silently truncating context on roughly every other turn. `parallel = 3` (174762/slot) was also checked as a middle ground — only 10.8% of requests would exceed it — but wasn't adopted either, since `--models-max 2` already removes the actual bottleneck that motivated touching `parallel` at all, and there's no evidence the remaining within-model queuing (2 slots, occasionally 3-4 concurrent subagents) is a real problem rather than a hypothetical one. Revisit `parallel` only with fresh evidence that queuing is actually costly, and re-check the token-count distribution before picking a number — don't guess a second time.

## Consequences

- VRAM/unified-memory usage rises from "one model resident" to "two models resident, permanently" — this is the whole point, but it means this stack no longer has the standing-memory headroom ADR 0005's single-warm-model design assumed. If a 3rd experimental profile is added later, decide then whether it should also get a permanent slot (`--models-max 3`) or fall back to on-demand eviction against these two.
- Concurrent requests within one model (e.g. >2 simultaneous subagents hitting `qwen3.8-27b`) still queue behind `parallel = 2`'s 2 slots rather than running fully in parallel. Unlike `--models-max 1`'s cross-model eviction, this queuing doesn't fail or truncate anything — it's added latency, not added risk — but it means 4-way subagent runs like the one that prompted this ADR will still serialize 2-at-a-time.
- `README.md`'s "How it works," "First-time setup," "Models" table, and "Verify GPU offload" sections updated to match (`--models-max 2`, `qwen3.8-27b` as default-warm, MTP GGUF source).
- `models/models.json`'s `qwen3.6-35b-a3b` entry now points at `unsloth/Qwen3.6-35B-A3B-MTP-GGUF`; the GitOps sync (`scripts/sync_models.py`) will download the new repo and remove the old `unsloth--Qwen3.6-35B-A3B-GGUF` directory automatically on the next push to `main` — no manual step on the DGX Spark itself.
